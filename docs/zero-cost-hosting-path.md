## Data recovery

1. Obtain a preservation confirmation and a consistent, authorized read-only export from MongoDB. The Atlas Admin API still returns HTTP 402. The November 13 support request is in Gmail Sent and no reply granting export access has arrived. Record the time or version of the snapshot, original inventory, per-collection counts and index metadata. Save the original and checksums in encrypted storage with restricted access.
2. Rehearse recovery using a MongoDB Community version compatible with the source snapshot and a new isolated database. Use the vendor's restore procedure for snapshots or oplog replay when applicable. Keep TTL jobs, application writes, push, email, Stripe, and other external effects disabled during comparison. Run the offline BSON staging and verification commands in the [Cloudflare lab README](../cloudflare-poc/README.md). If the export is partial, keep it and mark every missing collection explicitly. Verify source completeness before projecting records into relational tables. [MongoDB Database Tools](https://www.mongodb.com/docs/database-tools/) · [MongoDB restore procedure](https://www.mongodb.com/docs/database-tools/mongorestore/)
3. Preserve original BSON `_id` values and LetsGoRide application `id` values independently. Check references across users, drivers, vehicles, trips, ride requests, courier and food fulfillment, and Operations. Reconcile wallet and fee ledger rows, statements, payouts and Stripe identifiers by account, currency and amount. Compare counts, indexes, audit history and totals. Keep unresolved references, duplicate business IDs, unsupported data and unknown provider results in the reconciliation report for resolution before promotion.
4. Plan session handling before any recovered login goes live. Preserve password hash, scheme, salt and work factor. Recover account status, verification and role grants. Protect secrets for encrypted payout, private document and handoff data. Review expiry and revocation for old sessions and one-time challenges and reconcile external private media separately. Keep real records in a protected recovery environment.

The deployable Worker serves liveness and returns 503 for readiness and product requests. Its sample configuration disables public routes and previews. The business test Worker is excluded from the deployable entry point. The local FastAPI fallback preserves MongoDB semantics and current mobile contracts. An already-owned always-on host with isolated networking, encrypted backups, monitoring, enough capacity and a tested recovery time is the lowest-change candidate for that fallback. Local testing alone leaves its production availability unverified.

Capacity example using the mobile app's configured 4-second interval for active drivers. If 20 drivers continuously send one Worker request and one D1 row update every four seconds for six hours, those updates alone consume 108,000 requests and at least 108,000 row writes. Keep active-trip safety, operations visibility and financial reconciliation available through a tested fallback.

## Release and rollback

1. Keep this migration on its draft branch while export, domain parity, dependency audit, isolated provider and account access, and quota/load checks are open. Run real CI after the GitHub Actions account lock is resolved. GitHub's billing annotation says jobs never started. A local passing run supplies independent evidence while that lock remains.
2. Before promotion, capture a recoverable backup of the verified source and target, record the pre-cutover endpoint, deployment IDs and provider webhook ownership, and rehearse restoring the previous app against the verified database. Render currently returns 503 and is unavailable as a rollback target. A healthy destination with a verified copy of recovered data is required before switching.
3. During a future cutover, stop admitting new rides, orders and payouts in the agreed window. Drain or reconcile in-progress work, capture and verify the final delta, then switch one writer and one payment consumer at a time. Confirm login, dispatch, order fulfillment, Operations, WebSockets, notifications and reconciliation before reopening writes broadly. Track outage, error-rate, dispatch-age, support and payment thresholds and a named on-call owner.
4. If smoke checks fail or state diverges, pause admission and settlement consumers, preserve target state and logs, reconcile any target writes and unknown provider outcomes into the recovery database, and restore traffic only to the last healthy verified deployment. Keep the same provider idempotency keys for retries. Avoid dual writers and avoid replaying captures or payouts from an older backup without provider reconciliation. Run the same functional checks before reopening. If no verified rollback target exists, keep the affected features in maintenance.
